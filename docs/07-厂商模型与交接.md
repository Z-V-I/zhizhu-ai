# 厂商与模型：谁决定什么

> 一句话：**用户只选「厂商」，管理员决定「这家用哪个型号」，换型号对用户不可见。**

---

## 1. 为什么分成两层

如果直接把厂商的模型名（`deepseek-chat`、`qwen3-max`、`glm-4.6`）暴露给用户，会有三个后果：

1. 厂商一改型号名、下线旧型号，用户那边就报错，而这不是你能提前通知的事
2. 用户会开始比较「哪个型号强」，然后反复横跳，聊天质量反而下降
3. 你想换更便宜的同家型号时，得让所有人改习惯

所以对外只有 8 个**稳定代号**：

```
deepseek  qwen  glm  hunyuan  minimax  gpt  gemini  grok
```

代号背后挂哪个真实模型，存在数据库里，由 `/admin` 决定。厂商换代时用户完全无感。

---

## 2. 数据流

```
用户在界面选「通义千问」
        ↓  model = "qwen"
LibreChat 自定义端点 → Brain
        ↓  providers.target("qwen")
        ↓  ← 读 providers 表：base_url + 解密的 Key + 管理员选的 model_id
真实请求 https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions
        ↓  body.model = "qwen3-max"（用户在界面永远看不到这个）
```

**注意**：`/v1/models` 只返回已启用、有 Key、且选了模型的厂商。少一个不是 bug，是那家没配完。

---

## 3. 管理面板怎么用

打开 `https://你的域名/admin`，输入 `.env` 里的 `ADMIN_TOKEN`。

每家一张卡，四步：

1. 粘贴 API Key → 保存（用 Fernet 加密后进 Postgres，不落明文文件）
2. 点「拉取模型列表」→ 服务端调厂商的 `/models`
3. 从下拉里选一个 → 保存并启用
4. 打开聊天界面，那家就出现了

**拉不到列表的三家（MiniMax / 混元 / 智谱）** 是正常现象：它们的 `/models` 时有时无。点「手填」，直接把模型名写进去即可——这就是为什么面板允许手填，而不是强行要求从列表里选。

失败信息会原样显示在卡片下方（例如 `HTTP 401: Authentication Fails, Your api key ... is invalid`）。**这条信息很有用**：它证明请求真的到了厂商，只是 Key 不对，而不是网络不通。

`ADMIN_TOKEN` 为空时，整个面板和接口直接 503，不会留半开的口子。

## 4. 聊天中途换模型：为什么会掉质量，怎么修的

### 真正的原因

不是"上下文丢了"。LibreChat 每次请求都带上完整历史，上下文一直在。

掉质量的原因是：**新模型把前面那些 assistant 消息当成「自己说过的话」**。于是它去延续一个不属于自己的口吻、重复已经给出的结论、甚至把上一个模型的错误当成既定事实继续推理。换的厂商越"性格鲜明"，掉得越明显。

### 有没有现成项目能解决

- **LiteLLM / OpenRouter**：只做路由，不做交接，换模型是它的事外
- **RouteLLM（LMSYS）**：按难度把*单次*请求路由到强/弱模型，不跨轮次
- **LobeHub**：会给每条消息标记是哪个模型生成的（历史可读性），但**没有**跨模型的交接机制
- **Graphiti / Mem0**：管长期记忆，不管"这一次换人怎么说"

结论：**没有开箱即用的项目做这件事**。它不是一个库的问题，是一句提示词的问题。

### 我们的做法：交接说明（handoff）

`context.py` 里的 `_handoff()`，在检测到换厂商时注入三句话（约 90 token）：

```
【交接说明】
这条对话前面的回复由另一个模型（DeepSeek）生成，用户刚切换到你。
1. 那些回复不是你写的，不要模仿它们的口吻、长度和口头禅。
2. 它们已经给出的结论不要重复，直接在此基础上往下说。
3. 用户没问「是不是换模型了」就不要提这件事。
4. 如果你判断前面有错，简短纠正一句就继续，不要长篇复盘。
```

检测靠 `conversation_state` 表：每次请求记下 `(conversation_id, model)`，一次和上次不同就是切换。**这是唯一的判断依据**——LibreChat 不会告诉你"用户刚换了模型"。

成本对比：重新摘要整段对话约 1500 token 且要等一次模型调用；交接说明 90 token、零延迟。

### 顺带做的一件事

`provider_note()` 给不同厂商不同的中文约束（Gemini 别复述背景、推理模型不输出思考过程、OpenAI 系保留专有名词原文）。同一套提示词喂 8 家，效果能差一倍，这几句是"每家都好用"和"能切但难用"的分界。

## 5. 删掉了什么

`librechat.yaml` 里 `endpoints.agents.capabilities` 设成空数组 `[]`，也就是**白名单里什么都不放**：

| 关掉的 | 原本能干什么 |
|---|---|
| `skills` | 挂载技能包 |
| MCP 工具（`tools` / `deferred_tools`） | 接外部工具服务器 |
| `execute_code` | 跑代码 |
| `file_search` / `ocr` | 检索上传的文件 |
| `web_search` | 联网搜索 |
| `artifacts` / `subagents` | 生成可运行产物 / 派子智能体 |
| `actions` / `ask_user_question` | 调外部 API / 反问表单 |

现在 Agent 构建器里只剩「名字、头像、提示词、模型」——正好是要的那四样。

**为什么这是删对了**：这些能力每一个都需要额外的常驻服务或稳定的外部依赖（RAG 要向量库、代码执行要沙箱、MCP 要逐个调通）。2C4G 上开着它们的结果不是"功能多"，是"每个都半坏"。RAG 那条警告 `RAG API is either not running or not reachable` 就是证据。

## 6. 智能体市场：查过了，没有能接的 API

LobeHub 的市场调用链在源码里是 `lambdaClient.market.*`（tRPC），且每次请求前要 `safeInjectMPToken()`——**必须是他们自己的登录态**。

实测从服务器直接请求：

```
403  https://market.lobehub.com/api/v1/agents    → "Just a moment..."（Cloudflare 挑战）
403  https://market.lobehub.com/api/v1/skills
403  https://market.lobehub.com/api/v1/plugins
```

**结论：没有可以拿 API Key 接入的市场服务。** 想接就得模拟浏览器 + 维持登录态，属于随时会坏的那种依赖，个人项目不该背。

所以走第二条路：**预置 + 自建**。

已预置 6 个（创建在你账号下，可改可删）：

| 名字 | 定位 | 特点 |
|---|---|---|
| 小满 | 聊天伙伴 | 短句、不说教、先接情绪 |
| 老陈 | 技术顾问 | 先结论、明说代价、不堆术语 |
| 教练 | 学习教练 | 先举例再抽象、答错先找哪步想歪 |
| 润笔 | 文字润色 | 保留原作者语气，列出改动理由 |
| 谋士 | 决策陪练 | 先问清约束、最后把选择权交回去 |
| 译手 | 翻译与外语 | 像目标语言本来就这么写，不逐字对齐 |

用户可以自由新建：名字、头像、提示词、选厂商。不发布、不互动、不上市场——这是刻意砍的，不是没做。

## 8. 已接通的真实配置（2026-11-19）

三家自有 Key 打通了 9 张卡，其中 6 张是「借」聚合的 Key：

| 卡片 | 实际型号 | 走的通道 | Key 来源 |
|---|---|---|---|
| DeepSeek | `deepseek-v4-pro` | 官方直连 | DeepSeek 自己的 |
| MiniMax | `MiniMax-M3` | 官方直连 | MiniMax 自己的 |
| ChatGPT | `openai/gpt-6.2-astra` | OpenRouter | 借聚合 |
| Gemini | `google/gemini-4-hydrogen` | OpenRouter | 借聚合 |
| 通义千问 | `qwen/qwen4-max` | OpenRouter | 借聚合 |
| 智谱 GLM | `z-ai/glm-5.3` | OpenRouter | 借聚合 |
| Grok | `x-ai/grok-4.7` | OpenRouter | 借聚合 |
| 腾讯混元 | `tencent/hy4` | OpenRouter | 借聚合 |
| 聚合 | `google/gemini-3.5-flash` | OpenRouter | 自己的 |

**「借 Key」是什么**：卡片上写 `params.key_from = "openrouter"`，`providers._key_for()` 在自己没 Key 时去那张卡取。
好处是换聚合商只改一处，坏处是删掉聚合卡会连带 6 张卡一起哑（这是有意的耦合，不是 bug）。

**embedding 也靠聚合**：`params.embed_model = "openai/text-embedding-3-small"`，维度 1024。
OpenRouter 的 `/embeddings` 实测可用（`dimensions` 参数生效），所以不需要额外买通义的 Key。

**内部杂活模型**：`.env` 里 `CHEAP_MODEL=deepseek:deepseek-flash`。
冒号语法是给「摘要 / 抽记忆 / 起标题」用的：同一家换个便宜型号，不必为此多开一张卡。
别用 reasoning 型模型干这活——它会把 800 个 token 全烧在思考上，`content` 返回空，抽取静默失败（踩过）。

### 这一轮修掉的真 bug

1. `providers.save()` 的占位符整体错位一位（`$1` 从没被赋值、`WHERE` 多要一个参数），
   asyncpg 报的是 `could not determine data type of parameter $1`——完全看不出是参数编号问题。
   表现是管理面板「选好型号 → 保存」永远 500，但「填 Key」「拉列表」都正常，很容易误判成前端问题。
2. `params` 是 jsonb，传字符串必须显式 `::jsonb`。
3. `librechat.yaml` 必须 `enforce: true`，否则模型选择器里会混进 openAI / google / anthropic
   这些没配 Key 的内置端点，点进去必报错。
4. 关掉 MCP 面板用 `interface.mcpServers.{use,create,share}: false`，不是删代码。

## 9. 改成「只聊天、最便宜」之后的配置（2026-11-19 下午）

上一版选的是各家的旗舰，用来聊天纯属浪费。这一版按 **"够聊 + 单价最低"** 重选，
并且把「思考」关掉了——这是省钱的大头，不是小数点。

| 卡片 | 型号 | 输入/M | 输出/M | 关思考 |
|---|---|---|---|---|
| DeepSeek | `deepseek/deepseek-v4-flash` | $0.090 | $0.180 | ✅ |
| 通义千问 | `qwen/qwen3.7-flash` | $0.030 | $0.130 | ✅ |
| 智谱 GLM | `z-ai/glm-4.7-flash` | $0.061 | $0.400 | ✅ |
| 腾讯混元 | `tencent/hy4-flash` | $0.035 | $0.140 | ✅ |
| Gemini | `google/gemini-2.5-flash-lite` | $0.100 | $0.400 | 本身不思考 |
| ChatGPT | `openai/gpt-4.1-nano` | $0.100 | $0.400 | 本身不思考 |
| Grok | `x-ai/grok-4.20` | $1.250 | $2.500 | ✅ |
| MiniMax | `MiniMax-M3.1-Flash`（直连） | $0.150 | $0.600 | ❌ 官方不允许关 |
| 聚合 | `qwen/qwen3.7-flash` | $0.030 | $0.130 | ✅ |

**为什么关思考比换型号更重要**：测下来 deepseek-flash 回答「你好」要吐 77 个思考块，
GLM/混元/gpt-5-nano 甚至会把 400 token 的预算全烧在思考上、正文一个字不剩。
关掉之后同样一句「你好」首字延迟从 2-5 秒降到 1 秒内，token 消耗降一两个数量级。

**怎么关**：厂商卡 `params.body = {"reasoning": {"enabled": false}}`，
`upstream.prepare()` 用 `setdefault` 合并进请求体（不覆盖调用方显式传的值）。
不是所有模型都支持——gpt-5-nano 会 400 `Reasoning is mandatory`，所以它换成了 4.1-nano。

**DeepSeek 也走聚合了**：官方 API 没有关思考的开关，走 OpenRouter 才能关。
单价一样（$0.09/$0.18），实际花费差几倍。你自己的 DeepSeek Key 仍然存在卡片里，
想改回直连就把 base_url 改回 `https://api.deepseek.com/v1`、删掉 `key_from`。

### 顺带修掉的崩溃

`Cannot use 'in' operator to search for 'tool_calls' in undefined`

根因在 `/app/node_modules/@librechat/agents/src/llm/invoke.ts:771`：
`result.messages?.flatMap(m => 'tool_calls' in m ...)`，`messages` 里混进了 `undefined`。
触发条件是**上游把 `delta.content` 发成 `null`**——推理型模型在思考阶段的每个块都是
`{"content": null, "reasoning_content": "..."}`。Gemini/GPT 这类不思考的模型永远不发 null，
所以「换了个厂商就崩」看起来像玄学。

修法在网关的 `relay()`：从逐字节透传改成逐行重发，`_fix_sse_line()` 把
`content: null` 改成 `""`。代价是每块多一次 JSON 解析（个人站可忽略），
换来的是所有推理模型都能正常聊天。
兜底也改了：上游全挂时不再只发 `{"error": ...}`（前端同样会崩），
而是发一条正常的 assistant 文本 `[上游出错] ...`，用户至少看得懂。
