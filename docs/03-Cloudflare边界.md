# Cloudflare 边界：能用到什么程度

> 结论：**不能全 CF，但可以"CF 管边缘、一台小机器管重活"**。这不是妥协，是运行时模型决定的硬边界。

---

## 1. 一句话回答

Cloudflare 的边缘能力（DNS / WAF / Access / Pages / R2 / CDN / Tunnel）几乎能全覆盖你的**外围**需求；
但 **LibreChat、LiteLLM、Mem0 都是"长期运行的进程 + 原生依赖 + TCP 数据库连接"**，Workers 的运行时装不下。
强行全 CF，等价于放弃"用成熟聊天前端"，自己重写一个。

---

## 2. 逐组件映射

| 你的需求 | 全 CF 方案 | 可行度 | 真实情况 |
|---|---|---|---|
| 域名 / TLS / CDN / WAF | CF 代理 | ✅ | 本来就该用，免费额度足够 |
| **只对朋友开放** | **Zero Trust Access**（邮箱 OTP + 白名单） | ✅ **强烈推荐** | 50 人以内免费，直接替掉"邀请码系统"，省一周开发 |
| PWA 静态壳 | Pages | ⚠️ | 只有自研前端才行；LibreChat 的前端要和它的 API 同源部署 |
| 聊天前端 | Containers（beta） | ❌ | 无持久盘、闲置休眠冷启动、Mongo 跑在里面是运维灾难 |
| 模型网关 | **AI Gateway** | 🅱 部分 | 支持主流 provider + 自定义 OpenAI 兼容端点，但**没有 LiteLLM 的虚拟密钥/按人预算/模型别名**这套 |
| 记忆元数据 | D1（SQLite） | ⚠️ | 能存，但没有 JSONB、复杂查询弱，将来想搬去 Postgres 会疼 |
| 向量检索 | Vectorize | ✅ | 能替 pgvector，但 **Mem0 开源版是 Python 库，跑不了** → 要么自己写检索，要么买 Mem0 托管 |
| 任务队列 | Queues | ⚠️ | 能出队，但 Worker CPU 时间有限，解析 500MB 的 ChatGPT 导出包跑不完 |
| 备份 / 导出包 | **R2** | ✅ **强烈推荐** | 零出口费，pg_dump 直接推上去 |
| 入站不暴露端口 | **Tunnel** | ✅ | 家里 NAS/旧电脑也能上线，不用买公网 IP |
| **出站访问 OpenAI/Gemini** | Workers 出网 | ⚠️ **最大坑** | 见 §3.1 |

## 3. 三个必须先知道的硬约束

### 3.1 Tunnel 只解决"进来"，不解决"出去"

这是最容易被忽略的一点：`cloudflared` 是**入站隧道**，它让你的服务能被公网访问，但**不会改变你家宽带访问 OpenAI 的路由**。
所以"家里跑 + CF Tunnel"这条路，聊天前端能上线，但 **8 家里有 3 家（GPT / Gemini / Grok）调不通**。

WARP 能不能救？理论上能让出站走 CF 网络，但 CF 的 IP 段被 OpenAI 风控的概率不低，实测稳定性不可靠。**别把主链路压在这上面。**

→ **结论：仍然需要一台新加坡/日本的小机器，因为你需要的是"出站位置"，不是"入口"。**

### 3.2 Workers 出口 IP 的地区问题

就算你把 brain 改写成 Worker，它调 Gemini 时出口 IP 由 CF 边缘节点决定。中国大陆用户请求打到 HK 边缘，出口很可能被判为不支持区域 → 403。
这是"全 CF"方案里最隐蔽的雷。

### 3.3 D1 没有 pgvector，Mem0 就用不了

Mem0 开源版是 Python 包，且需要一个向量库后端。全 CF 等于：**自己实现"抽取 + 检索"**，那就不是"用开源项目"，是"重写 Mem0"。工作量比你现在整个胶水层还大。

## 4. 三条路线，选一条

### 路线 A · 真·全 CF（不推荐）

```
Pages(自研前端) + Workers(Hono) + D1 + Vectorize + AI Gateway + Access + R2 + Queues
```

- 得到什么：运维几乎为零，全球边缘，账单接近 0。
- 付出什么：**"不造 UI"这条原则作废**。你要自己写聊天界面、流式渲染、Markdown、代码块、文件上传、会话管理、Agent 编辑……这是这个项目 70% 的工作量。
- 只在这种情况下选它：你本来就打算写一个自己的聊天前端，或者你只想做"记忆中心 + 迁移中心"这一个产品，聊天用别人家的。

### 路线 B · CF 边缘 + 一台小机器（✅ 推荐）

```
用户 ── CF(DNS/WAF/Access) ──► SG/JP VPS
                                 ├─ Caddy → LibreChat(api+client)
                                 ├─ Brain（记忆/UMF/迁移）
                                 └─ LiteLLM ──► 8 家模型
        R2 ◄── 每日备份          Pages ◄── 记忆中心的静态资源（可选）
```

- CF 承担：DNS、TLS、WAF、**Access 登录**、R2 备份、可选 Tunnel。
- 小机器承担：所有需要"活着"的东西 + **出站位置**。
- 成本：VPS ¥120–220/月，CF 免费额度够用。
- **这是唯一能同时满足"用成熟 UI"和"免翻墙调 8 家"的组合。**

### 路线 C · 全自托管（最省事，但少一层防护）

一台 VPS + Caddy 直连，CF 只做 DNS。适合先跑通、后加防护。**M0 建议从这里起步**，M1 再把 CF 的 WAF/Access/R2 接上——它们是叠加的，不影响已有架构。

## 5. 落地建议（按性价比排序）

| 优先级 | 用 CF 做什么 | 怎么接 |
|---|---|---|
| P0 | DNS + 橙云代理 | 域名解析直接开，WAF 免费规则够用 |
| P0 | **R2 备份** | `pg_dump \| rclone` 到 R2，每日一次，保留 14 天。记忆是你的核心资产 |
| P1 | **Access 保护管理面** | 只保护 `/umf-ui/*` 和后台入口，**不要保护整个站**（见下方坑） |
| P2 | AI Gateway | 挂在 LiteLLM 前面做统一看板/缓存；注意多一跳延迟 |
| P3 | Tunnel | 只有在你决定"不买 VPS、跑家里"时才需要，且必须另配海外出站 |
| ✗ | Containers / D1 / Vectorize | v1 全部不用 |

**Access 的坑（重要）**：如果整站套 Access，再叠加 LibreChat 自己的登录，就是两层认证；iOS 把 PWA 加到主屏后，独立模式的 cookie 作用域偶发失效，会出现"每次打开都要重新验证"。
→ 正确做法：**Access 只管记忆中心和管理页**，聊天主站用 LibreChat 登录 + 邀请码。这样"只对朋友开放"有两道闸，且互不干扰。

---

## 6. 所以，方案文档里改了什么

1. `docker-compose.yml` 增加可选的 `cloudflared` 服务（`docker-compose.tunnel.yml` 覆盖层），**默认不启用**。
2. Caddy 保留——即使上了 CF，本机仍需一层反向代理来处理 SSE 不缓冲和路径分流。
3. 备份目标从"对象存储"明确为 **R2**（零出口费，最适合导出大 zip）。
4. 邀请码系统降级为 P2：先用 **Access 白名单 + 手动开户**，人多了再写邀请码，能省一周。
