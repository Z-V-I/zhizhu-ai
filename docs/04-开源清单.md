## 2. 对话压缩：选 LLMLingua-2

### 为什么是它

- **微软出品、MIT、还在维护**（最后一次提交 2026-11），不是个人玩具。
- **LLMLingua-2 是"token 分类"路线**：用一个小编码器判断每个 token 该不该留，比第一代的"困惑度筛选"快 3–6 倍，且**天然支持中文**（XLM-R / 多语 BERT 底座）。
- 模型只有几亿参数，**纯 CPU 能跑**，不用占一张显卡。
- 输出可控：`rate=0.6` 就是"保留六成 token"，可预测。

### 但它是第二层，不是第一层

这是我要跟你掰扯清楚的一点：**"压缩对话"和"压缩文档"是两件事。**

| | 长文档 / 日志 / 粘贴的代码 | 多轮聊天 |
|---|---|---|
| 冗余在哪 | 词句层面（废话、重复修饰） | **语义层面**（说过又绕回去、寒暄、试错） |
| token 级压缩效果 | 好，压 40–60% 几乎不掉信息 | **差**，会把"我不同意"压成"同意" |
| 正确工具 | LLMLingua-2 | **滚动摘要** |

真正的聊天压缩，OpenAI / Claude 用的都是"滚动摘要 + 结构化状态"，不是 token 裁剪。
所以本项目做**三层**，按成本从低到高，只在需要时逐层启用：

```
第 1 层  结构裁剪    保留最近 8 轮 + 首条指令，零成本，永远可用
第 2 层  滚动摘要    超预算的老对话 → cheap-extract 压成 400 字，落库缓存复用   ← 主力
第 3 层  LLMLingua-2 单条消息 > 1500 token 且是"用户粘贴的大段文本"时启用        ← 精准补刀
```

代码位置：`deploy/brain/app/compress.py`，第 3 层没装依赖会自动降级成"保留头尾"，**不会阻塞请求**。

### 考虑过但没用的

| 候选 | 为什么不用 |
|---|---|
| `langchain` 的 `ConversationSummaryBufferMemory` | 2024 年起已进入弃用轨道，官方建议自己实现；为了一个 30 行的策略引入整个框架不划算 |
| `sumy`（TextRank/LexRank） | 抽取式摘要，只适合新闻长文，对话里抽出来的句子会像电报；且中文要额外接 jieba |
| `LLMLingua` 第一代 | 需要一个小 LM 算困惑度，慢且对中文不友好，已被二代取代 |
| 上 Graphiti 做"语义压缩" | 那是记忆图谱，不是压缩；两回事 |

**结论：压缩用 LLMLingua-2，但把它放在第三层；主力是滚动摘要，那个不需要库，只需要纪律。**

## 4. 为什么不再引入 Dify / LangGraph / Letta

你最初列的这三个，我都认真评估过，结论是**全是负收益**：

- **Dify**：自带一套用户体系、一套 Agent 管理、一套工作流。接进来等于在你的站里再开一个站，用户要在两个系统里各有一份身份。而 LibreChat 的 Agent 已经覆盖"自定义角色"的全部需求。
- **LangGraph**：它是"写 Agent 的框架"，不是"跑 Agent 的服务"。你要的是给朋友用的产品，不是给开发者用的 SDK。
- **Letta**：它会**接管整个对话循环和记忆所有权**，和 LibreChat 的 Agent 层正面冲突。二选一的话，选前端。

一句话：**每多引入一个"平台级"项目，就多一套用户体系和记忆，而你的核心卖点恰恰是"只有一个大脑"。**
