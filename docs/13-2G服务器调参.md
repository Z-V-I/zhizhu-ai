# 2 GB 机器上跑这套栈

> 结论：**能跑，但要调参 + 加 swap，而且没有长期增长余量。**
> 数据量或用户数上来之前，建议升到 4 GB。

## 为什么 2 GB 会紧张

实测（4 GB 机器、清空数据后）：

| 容器 | 峰值 |
|---|---|
| api（LibreChat/Node） | 537 MB |
| mongodb | 512 MB（顶到 limit） |
| postgres + pgvector | 117 MB |
| caddy | 64 MB |
| brain | 72 MB |
| **合计** | **1302 MB** |
| Docker + 系统 | ~300 MB |

2 GB 机器 `free -m` 显示总内存 1676 MB、可用约 1300 MB。默认参数下正好压线，
一旦有人上传大文件、或 Mongo 长到几万条消息，就会 OOM。

## 怎么调

用 `docker-compose.2g.yml` 覆盖层，不要直接改 `docker-compose.lite.yml` ——
后者是 4 GB 机器上的正解，改坏了以后换机器还得改回来。

```bash
docker compose -f docker-compose.lite.yml -f docker-compose.2g.yml up -d
```

它做三件事：

| 项 | 默认 | 2 GB 上 |
|---|---|---|
| MongoDB WiredTiger 缓存 | 0.25 GB | **0.1 GB**（省 150 MB） |
| api 内存上限 | 768 MB | **560 MB** |
| mongo / pg / brain / caddy 上限 | 512 / 384 / 384 / 128 | 320 / 320 / 280 / 96 |

`api` 限到 560 MB 的理由：真到极限时让它先死（重启即可恢复），
而不是让内核去挑更贵的目标（Mongo 崩了要修数据）。

## swap：不是性能手段，是保险

```bash
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo "/swapfile none swap sw 0 0" >> /etc/fstab
```

它的作用是"某天某个容器突然涨上去"时，给 OOM killer 留出时间只杀一个容器，
而不是把整机拖死。**不要指望它扛日常负载** —— Node 一旦被换到磁盘，
每次回复都会先卡几秒，而且是持续的。

## 什么时候必须升级

出现下面任一情况就该加内存：

- `free -m` 的 available 长期低于 200 MB
- `docker stats` 里 api 的内存贴着 limit 不动（说明它一直在被压）
- dmesg 出现 `Out of memory: Killed process ... node` 或 `mongod`
- 有 5 个以上用户同时在传文件

## 监控一条命令

```bash
free -m; docker stats --no-stream --format "table {{.Name}}\t{{.MemUsage}}\t{{.MemPerc}}"
```
