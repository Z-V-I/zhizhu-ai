# LobeHub v2 对照 + 服务器选型

> ⚠️ **预算修订**：本文 §4 给的是"不砍组件"的配置（4C8G）。最终确定预算 ¥50–100/月、阿里云新加坡 2C4G，
> 对应的「砍 LiteLLM + 零构建前端 + 0.8–1.2 GB 常驻」方案见 **`docs/06-低成本部署.md`**。选型逻辑（§1–§3）仍然有效。

> 结论先行：**LobeHub v2 原生就带"结构化用户记忆 + 阈值自动压缩"，能力比我写的 brain 更成熟；但它没有 UMF、记忆抽取依赖 QStash 队列。所以底座不换，把它当"设计参考 + schema 来源"。服务器买 4C8G / 100G NVMe / 东京或新加坡。**

## 1. 有 LobeChat 系的源项目吗

有，但都加在别的地方，没有一个是加"可迁移记忆"的：

| 项目 | 基于 | 加了什么 | 对你有没有用 |
|---|---|---|---|
| `vual/lobe-chat-pro` | lobe-chat | 计费、充值、无限画布、绘图/音乐/视频面板、后台管理 | 无（你不收费、不做画图） |
| `ELIOWANG/lobe-chat-fork` | lobe-chat | 原版镜像 fork，同步上游 | 无（就是同一个东西） |
| `IuaiChat` | lobe-chat | 知识库 + 多模态，Vercel/Worker 部署 | 无（你要的本地全栈） |
| 各类"中转站特别版" | lobe-chat | 对接 one-api / new-api，纯前端 | 无（你已经自建 LiteLLM） |

社区 fork 的动机几乎都是**变现**（计费、画图、卖中转），而你的动机是**长期陪伴 + 记忆可携带**，这两件事正交。所以 fork 生态里抄不到你要的核心。

## 2. 它确实自带自动压缩，而且不止压缩

`vendor/lobehub`（稀疏拉取，24MB，commit `a8c7521` 2026-11-19）里翻到的实证：

### 2.1 上下文自动压缩

`packages/types/src/agent/chatConfig.ts`：

```ts
/** Enable context compression
 *  When enabled, old messages will be compressed into summaries when token threshold is reached */
enableContextCompression?: boolean;
```

配套还有 `src/store/chat/slices/agentRun/.../conversationLifecycle/compression.ts`，做法是：

1. 老消息**成组**折叠（`role: 'compressedGroup'`），生成一条摘要消息；
2. 摘要走正常 chat 端点流式生成，边生成边替换气泡（用户能看见它在压）；
3. **失败整组回滚**（`cancelCompression`），不会把历史压成空白；
4. `/compact` 手动命令走同一条链路；
5. 前端可**展开**压缩组看原文（`features/Conversation/Messages/CompressedGroup/`）。

这比我 brain 里的"滚动摘要写进 system prompt"体验好一档——你的用户看得见"哪段被压了、压成了什么"，而我的做法对前端完全透明，压掉了什么用户不知道。

### 2.2 更重要的：整套用户记忆

`apps/server/src/services/memory/userMemory/` 下有完整实现：

```
extract/          逐 topic 抽取 → gatekeeper 过滤 → 落 5 层
  ├─ extractTopic.ts / persistLayers.ts / runtime.ts
consolidation/    冲突合并（旧记忆被新记忆取代）
persona/          汇总成"用户画像"文本
embedding.ts      向量化
../searchParams.ts 检索
workflows/hourly.ts   每小时批量扫未抽取的 topic
```

五层 schema（`apps/server/src/globalConfig/parseMemoryExtractionConfig.ts`）：

```ts
const MEMORY_LAYERS = ['activity', 'context', 'experience', 'identity', 'preference'];
```

对应的前端面板是 `features/Conversation/WorkingSidebar/Memory/`，可看、可编辑、可删。Agent 级开关是 `chatConfig.memory = { enabled, effort, toolPermission }` —— **每个 Agent 单独决定要不要读记忆、能不能写记忆**。

也就是说，"一个大脑 + 多个智能体 + 记忆边界"这件事，它已经有产品级实现，而且比 Mem0 的扁平条目更接近"人格建模"。

### 2.3 但自托管有两个硬成本

**① 记忆抽取是队列驱动的，不是同步的。**
`apps/server/src/router-hono/workflows/` 下全是 QStash 编排：`qstashClient.ts`、`qstashAuth.ts`、`hourly.ts`、`processUserTopics.ts`。自托管要么接 Upstash QStash（多一个境外 SaaS 依赖 + 一个要维护的签名密钥），要么自己写 cron 打那几个 webhook 端点。个人项目里这是**最容易半年后静默失效**的一环——它不报错，只是"不再记住新东西"。

**② 记忆没有出口。**
五层记忆存在它自己的 Postgres schema 里，没有导出协议，也没有迁移导入。你把它当底座，UMF 还是得自己写一遍，而且要从它的 5 张表 + persona 反向适配。**你最核心的差异化，它一点忙帮不上。**

### 2.4 顺带修正一个我之前的说法

我之前说"LibreChat 只有 summarize 开关"。查了源码，说法要更准：

- `client/src/hooks/Chat/useCompactConversation.ts` 注释写明 **"Manual context compaction"** —— LibreChat 有压缩，但是**手动触发**（TokenUsage 旁边的按钮 / 命令），没有"超阈值自动压"。
- 压缩结果是一轮总结对话，**没有折叠组 UI**。

| 能力 | LobeHub v2 | LibreChat |
|---|---|---|
| 阈值自动压缩 | ✅ `enableContextCompression` | ❌ 只能手动 |
| 手动压缩命令 | ✅ `/compact` | ✅ `useCompactConversation` |
| 压缩组可展开看原文 | ✅ | ❌ |
| 压缩失败回滚 | ✅ | 部分 |
| 5 层结构化记忆 | ✅ 原生 | ❌ |
| 记忆面板 UI | ✅ | ❌ |
| 记忆导出 / 迁移 | ❌ | brain 负责 ✅ |
| 邀请码 | ❌（用 CF Access 替代） | ❌（用 CF Access 替代） |
| 许可证 | Community License（非商用放行） | MIT |

## 3. 所以换不换

**不换。** 三条理由，按分量排：

1. **它的强项正好是我不需要的，我的强项正好它没有。** 压缩和记忆面板它做得比我好，但那是"能聊得舒服"；UMF、迁移、时间线是"数据是我的"，那才是你要建这个站的原因。换过去，等于用 20 天工作量换一个"更好用但不能带走"的记忆。
2. **QStash 那一环对个人项目是负债。** 记忆抽取异步化在云上是对的（不能阻塞请求），在你这儿它意味着一个境外队列服务 + 一套签名密钥 + 一个"静默失效"的失败模式。brain 里这段是 `BackgroundTasks` 一把梭，丑但不会悄悄坏。
3. **它的 v2 是 2026-01 才重构的版本**，自托管路径（web + apps/server + Postgres + S3/MinIO）比 LibreChat 复杂一档，出问题可查的资料少。

**但要抄它三样东西**（这才是这轮调研的实际收益）：

| 抄什么 | 落到哪 |
|---|---|
| 五层记忆模型 `identity / preference / experience / activity / context` | `deploy/brain/app/schema.sql` 的 `umf_memory.layer` 枚举，替掉现在的 `kind: preference\|fact`。分层比扁平标签更能表达"人格"，也方便做时间线 |
| 压缩的**可见性** | `umf_summary` 表里存"哪几条消息被压成了什么"，在 `umf-ui` 的记忆中心里能展开看。不改 LibreChat 前端也能有"我能看见它记住了什么" |
| `consolidation`（冲突合并）语义 | 新记忆命中旧记忆时写 `supersedes` + `valid_to`，而不是覆盖。这是"观点什么时候变了"的数据基础 |

## 4. 服务器：先算账，再买

### 4.1 内存去哪了

| 容器 | 常驻 |
|---|---|
| Caddy | 30 MB |
| LibreChat（Node） | 400–600 MB |
| MongoDB 7 | 350–500 MB |
| Postgres 16 + pgvector | 250–400 MB |
| Redis 7 | 50 MB |
| LiteLLM（12 个别名） | 350–500 MB |
| brain（不带 torch） | 250–350 MB |
| brain + LLMLingua-2（torch） | **+900 MB ~ 1.2 GB** |
| Docker + 系统 | 400–700 MB |
| **合计** | **2.2–2.7 GB**（无 torch）/ **3.1–3.9 GB**（含 torch） |

再算**构建峰值**：`npm ci && npm run build`（LibreChat）额外要 1.5–2 GB，`pip install torch` 解包再要 1–2 GB。

结论很直接：

- **2C2G 会在 `npm run build` 那一步 OOM kill**，不是"慢一点"的问题。
- **4 GB 只能跑，不能建**，除非加 4G swap（能过，但构建从 8 分钟变 40 分钟）。
- **8 GB 是舒适线**：常驻 3–4 G，构建还有余量，LLMLingua 开着也不慌。

### 4.2 三档配置

| 档 | 配置 | 能干什么 | 月成本区间 |
|---|---|---|---|
| 最低可跑 | 2C4G / 60G SSD | 关掉 LLMLingua，构建靠 4G swap，构建时聊天会卡 | ¥60–120 |
| **建议** | **4C8G / 100G NVMe** | 全栈 + LLMLingua + 构建在同一台机器完成，20 人无压力 | **¥150–300** |
| 宽裕 | 8C16G / 200G NVMe | 还能顺手跑本地 embedding / rerank，或并行验证 LobeHub | ¥350–600 |

**推荐 4C8G。** 理由：核数不是给聊天用的（SSE 流式几乎不吃 CPU），是给**构建和 pip 装的**；内存不是给 20 个朋友用的，是给 torch 和 Node 构建用的。

### 4.3 买前必须确认的 7 件事

1. **区域：东京 > 新加坡。** 中国到东京 40–70 ms，到新加坡 70–110 ms。两地都通 OpenAI / Gemini / Grok。
2. **绝对不买香港。** OpenAI 与 Gemini API 都不把中国香港列为可用区域，会被 IP 拦。
3. **不买美国。** 延迟 180 ms+，打字机效果会一顿一顿，聊天体感直接崩。
4. **架构选 x86_64。** ARM 便宜，但 LiteLLM / torch 的 wheel 偶尔缺，省几十块不值。
5. **磁盘必须 NVMe。** Mongo 和 Postgres 都是小文件随机 IO，HDD 上查询会慢一个数量级。
6. **流量 ≥ 1 TB/月。** 纯文本 20 人每月不到 100 G，但朋友传图/传 PDF 会吃流量。
7. **先月付，别年付。** 8 家 API 的实际连通性和延迟要在真机上验，不合适就换机房，年付会锁死你。

### 4.4 别买清单

- ❌ **2C2G 低价年付机**：不是慢，是构建直接失败。
- ❌ **超售严重的"无限流量"大盘鸡**：构建 8 分钟变 2 小时。
- ❌ **GPU 机型**：LLMLingua-2 纯 CPU 跑得动，你不需要显卡。
- ❌ **国内备案节点**：8 家 API 里 3 家（GPT/Gemini/Grok）出站就有问题，还得备案。

### 4.5 下单后第一件事

```bash
# Debian 12 / Ubuntu 22.04
apt update && apt install -y docker.io docker-compose-plugin git curl

# 4G swap —— 构建兜底，不是日常用
fallocate -l 4G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile
echo '/swapfile none swap sw 0 0' >> /etc/fstab

# 先把镜像拉齐再构建，别让构建和拉镜像抢带宽
docker compose pull
docker compose build
docker compose up -d
```

如果之后决定**同时**验一下 LobeHub v2，配置要上调一档到 **16 GB**：它要跑 Next.js web + apps/server 两个 Node 进程，再加 Postgres 和 MinIO，8 GB 会很紧。

## 5. 一句话总结

LobeHub v2 证明了"结构化记忆 + 自动压缩"这条路是对的，而且它把 UI 做到了产品级；但它把记忆锁在自己的库里，而你要的是**记忆属于你**。所以：底座留 LibreChat，把它的五层模型和压缩可见性搬进 UMF，服务器买 **4C8G / 100G NVMe / 东京**。
