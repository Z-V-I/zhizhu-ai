## 1. 因为"非商业"，判断改了什么

| 项 | v1 的判断 | 现在 | 理由 |
|---|---|---|---|
| 前端许可证 | LobeHub 改后分发需商业授权 → 淘汰 | **不再是淘汰理由** | 个人非商用、不分发，社区许可证放行 |
| 前端选型依据 | 法务风险 | **纯工程成本** | 见下表 |
| 上游接入 | 自建 VPS / 中转二选一 | **自建网关 + 全部直连官方 API Key** | 你已明确 |
| 成本重心 | 控制总花费 | **控制上下文膨胀 + 别用贵模型做杂活** | 便宜模型单价已经很低 |

**前端仍然推荐 LibreChat，但理由换了**：不是许可证，是"你的胶水层往哪插最省事"。

| | LibreChat | LobeHub | Open WebUI |
|---|---|---|---|
| 语言/栈 | Node(Express) + React | Next.js + tRPC | Python(FastAPI) + Svelte |
| 接入记忆中间层 | **极简**：自定义 OpenAI 端点直接指过去，核心零改动 | 需在 tRPC 层插，或在 Next 路由里劫持 | 可用 Pipelines，机制天然支持 |
| 加邀请码/新页面 | Express 加路由 + React 加页 | App Router + tRPC 全套跟着改 | FastAPI 加路由最舒服 |
| 自带记忆与本方案的冲突 | 关掉即可（Mongo 里一个开关） | 自带 CRDT 记忆较深，需绕开 | 关掉即可 |
| PWA | 自己加（半天） | 原生最好 | 一般 |

> 一句话：**你是 Python 舒适区就换 Open WebUI，其它情况用 LibreChat。** 下面的 `librechat/librechat.yaml` 是唯一会作废的文件，其余全部复用。

## 2. 八家模型的接法（重点）

### 2.1 核心原则：国内全部走通用 `openai/` + `api_base`

LiteLLM 对各家的专用适配器（`dashscope/`、`zhipu/`、`minimax/`…）会随版本改名、参数映射也常变。而这 5 家**都提供 OpenAI 兼容端点**，直接用通用适配器 + `api_base`，升级永远不会炸。

| 别名（前端显示） | 厂商 | 实际端点 | 定位 | 成本档 |
|---|---|---|---|---|
| `ds-chat` | DeepSeek | `api.deepseek.com/v1` | **默认聊天 / 杂活主力** | 极低 |
| `ds-reasoner` | DeepSeek | 同上 | 深度推理 | 低 |
| `qwen-plus` | 通义 | `dashscope.aliyuncs.com/compatible-mode/v1` | 中文长文 / 高并发 | 极低 |
| `qwen-vl` | 通义 | 同上 | 看图 | 低 |
| `glm-4.6` | 智谱 | `open.bigmodel.cn/api/paas/v4` | 工具调用 / Agent | 低 |
| `minimax` | MiniMax | `api.minimax.chat/v1` | 长上下文聊天 | 低 |
| `hunyuan` | 混元 | `api.hunyuan.cloud.tencent.com/v1` | 备用 / 对比 | 低 |
| `gpt-5` | OpenAI | 官方 | 硬骨头 / 英文 | 高 |
| `gpt-5-mini` | OpenAI | 官方 | 轻量 | 中 |
| `gemini-flash` | Google | 官方 | **长文档 / 图片 / 便宜快** | 极低 |
| `gemini-pro` | Google | 官方 | 多模态主力 | 中 |
| `grok` | xAI | 官方 | 时效 / 观点类 | 中 |

> 具体 model id 以各家控制台当前值为准（各家改名频繁），`litellm/config.yaml` 里每行都有注释标明改哪里。

### 2.2 五家国内 API 从海外 VPS 调，行不行？

行。新加坡/日本 → 阿里云/腾讯云/智谱/深度求索，延迟通常 60–120ms，聊天场景无感（首 token 延迟主要来自模型本身，不是这 100ms）。**一台机器同时够得着国内和海外，这是选 SG/JP 而不是 HK 的唯一理由。**

### 2.3 真正需要适配的不是协议，是"脾气"

8 家模型的差异不在接口，在行为。这是很多人做多模型站最容易忽略的地方——同一个 system prompt 喂给 8 家，效果能差一倍。

Brain Gateway 里加一层 **provider 适配**（很薄，一个 dict 就够）：

| 差异点 | 处理 |
|---|---|
| 中文能力 | `gpt-5` / `grok` 中文输出偶尔夹英文；system 里显式要求"全程简体中文" |
| 系统提示词权重 | Gemini 对长 system prompt 的遵循度低于 OpenAI → 关键约束放到最后再说一遍 |
| 记忆注入位置 | 国内模型擅长"前置背景"；Gemini 更吃"对话中自然带出" → 记忆块位置按 provider 切换 |
| 推理模型 | `ds-reasoner` 不吃 `temperature`/`top_p` → 请求前剔除（`drop_params` 已兜底） |
| 工具调用 | Qwen/GLM 的 function call 格式差异大 → v1 只用 LibreChat 自带工具，不让 Brain 转译 |
| 空回复 | MiniMax/混元偶发返回空 content → 网关加一次重试 |

**这是"多模型"从"能切"变成"每个都好用"的分水岭。**

### 2.4 模型路由策略（省钱又不难用）

```
默认（闲聊、问答、改写）      → ds-chat       单价最低，中文好
长文/长文档/看图             → gemini-flash  上下文便宜、多模态
写代码/结构化输出            → glm-4.6 或 gpt-5-mini
硬推理（架构/数学/难 bug）    → ds-reasoner，失败降级 gpt-5
实时信息/观点                → grok
兜底                         → 任一家 429 时自动切下一家（LiteLLM fallbacks）
杂活（记忆抽取、标题、摘要）  → ds-chat（几乎白送，不要用 gpt）
```

`model_group_alias` 把 `cheap-extract` 指向 `ds-chat` —— 这样代码里永远写 `cheap-extract`，以后想换更便宜的只改一处。

## 3. 部署拓扑（单机，个人版简化）

```
新加坡/日本 VPS  4C8G  ── Caddy(443) ──┬── LibreChat :3080 ── Mongo / Meili / Redis
                                      ├── Brain  :8000  ── Postgres(pgvector)
                                      └── /umf-ui
                                             │
                                        LiteLLM :4000 ──┬── 国内 5 家（直连）
                                                        └── OpenAI / Gemini / xAI
```

个人版砍掉的东西：K8s、独立向量库（用 pgvector）、监控栈全套（先用 Uptime Kuma 一个容器）、对象存储（备份直接 `rclone` 到任意网盘）。

| VPS 规格 | 可行性 |
|---|---|
| 2C4G | 勉强能跑，必须关 Meilisearch、加 2G swap。**8 人以内够用** |
| **4C8G** | 推荐。全栈舒服，留了抽取/迁移的余量 |
| 2C2G | 不行，Mongo + PG 就吃满了 |

## 4. 成本（个人版，8 人以内）

| 项 | 月成本 |
|---|---|
| SG/JP VPS 4C8G | ¥120–220 |
| 域名 | ¥8（年付摊） |
| 聊天 API（8 人 × 日均 30 轮，七成走 ds-chat/qwen-plus） | **¥60–180** |
| 记忆抽取 + 标题 + 摘要（ds-chat） | ¥10–25 |
| embedding | ¥5 |
| **合计** | **¥200–450 / 月** |

关键结论：**你担心错方向了**。8 家便宜模型的聊天花不了钱，真正的成本黑洞是"上下文无限增长"——一个 200 轮不压缩的会话，单次请求就能顶别人一天。所以 §5.2 的分层注入和滚动摘要是省钱功能，不是体验功能。

省钱三条硬规则：
1. 杂活（抽取/标题/摘要）**永远**走 `cheap-extract`，代码里不许出现硬编码的贵模型。
2. 会话超过 30 轮自动滚动摘要，原文保留但不再进上下文。
3. 记忆注入总预算死锁 1200 token，超了就砍 L1 的条数，不砍 L0 画像卡。

## 5. M0 落地清单（本次已产出）

```
deploy/
├── docker-compose.yml        # 全栈：caddy/librechat/mongo/meili/redis/pg/litellm/brain
├── Caddyfile                 # TLS + SSE 不缓冲 + /api/umf 分流
├── .env.example              # 8 家 Key、JWT、DB 密码，逐项注释
├── litellm/config.yaml       # 12 个模型别名 + fallback + cheap-extract 别名
├── librechat/librechat.yaml  # Brain 自定义端点 + modelSpecs 预设
└── brain/                    # 网关骨架（透传，记忆逻辑留 TODO）
```

启动顺序与验收：

1. `cp .env.example .env` → 填 Key → `openssl rand -hex 32` 生成三个 secret。
2. `docker compose up -d` → `curl https://你的域名/api/umf/healthz` 返回 `{"ok":true}`。
3. `docker compose exec librechat npm run create-user` 手动开第一个号（个人版先关公开注册）。
4. 浏览器选 `Brain` → `ds-chat` → 发消息，**看到逐字流式输出**即 M0 通过。
5. 手机 Safari/Chrome 打开 → 添加到主屏 → 从图标启动，地址栏消失即 PWA 通过。

**M1 才做邀请码**：人少的时候手动开户 + `ALLOW_REGISTRATION=false` 已经安全，不必先写代码。
